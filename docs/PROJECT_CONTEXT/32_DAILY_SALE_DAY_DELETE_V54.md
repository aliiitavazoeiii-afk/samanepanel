# V54 — FULL DAILY SALE REPORT DELETE / REVERSAL

Date prepared in GitHub: 2026-09-05

## User requirement

On the active daily sales report page, beside **تقویم فروش**, add **حذف صورت روز**.

When used, the complete sales report for that SaleDay must be removed and every effect created by those sales must be reversed so balances return to the state they would have had without that day's sales.

This includes:

- normal Darma SaleLine rows,
- Takvin SaleLine rows,
- Anbaresh channel SaleLine rows backed by Darma stock,
- variable-color Darma `s3` rows,
- Dia Gallery rows,
- Digikala receivable entries generated by those SaleLines,
- Dia Gallery receivable entries generated by those Dia rows,
- physical stock previously deducted by those sales,
- SaleSnapshot rows belonging to deleted SaleLines (through the existing CASCADE relationship),
- SaleShortage / SaleAllocation child rows through the existing supported reversal/delete path.

After all sale-owned effects are reversed, the SaleDay itself is deleted so the calendar no longer shows that date as a registered sales report. Selecting the date again creates a fresh SaleDay through the existing calendar flow.

## Explicit scope boundary

This action is **NOT** a delete-everything-by-date feature.

Objects that merely have the same calendar date but are not owned by SaleDay remain untouched, including:

- payments,
- expenses,
- production,
- material operations,
- manual stock transfers,
- manual inventory corrections,
- returns,
- unrelated AccountEntry rows.

This boundary is important because the user asked to reverse what the daily sales report added, not all business activity on that date.

- route name: `daily_sale_day_delete`

## Reversal implementation

Core helper:

- `core.daily_report_actions_v21.delete_sale_day(day_id)`
- wrapped in `transaction.atomic`
- locks the SaleDay with `select_for_update`
- locks all SaleLine rows for that day
- locks all DiaGallerySale rows for that day

### Normal / Takvin / Anbaresh SaleLine

For each SaleLine:

1. set `quantity = 0`,
2. use the existing official inventory recalculation/reversal path,
3. call `sync_sale_receivable(line)` so the exact `sale:<id>:digikala` receivable entry is removed,
4. delete the SaleLine only after inventory + receivable reversal.

Normal/Takvin and Anbaresh use:

- `sync_sale_inventory_v19(line)`

This preserves the active V46 rule and, for Anbaresh, restores the exact recorded Darma allocation location/color rather than inventing independent Anbaresh inventory.

### Variable-color Darma `s3`

`s3` has no fixed ProductComposition and its exact colors come from SaleAllocation. Therefore V54 does **not** send it through the generic fixed-composition path.

It uses:

- `sync_variant_inventory(line, {})`

with the SaleLine quantity already zero. The variant engine first restores the existing exact allocations and then leaves the target at zero.

### Dia Gallery

For each DiaGallerySale:

1. set `quantity = 0`,
2. call `sync_dia_gallery_sale(line)`,
3. this returns `inventory_applied_quantity` to Darma HOME and removes its exact `dia-gallery:<id>:receivable` AccountEntry,
4. delete the Dia row.

Dia remains separate from Digikala and keeps its own receivable semantics.

## Historical safety guard

`SaleAllocation` is authoritative for what a normal SaleLine physically deducted.

If a SaleLine reports `inventory_applied_quantity > 0` but has no SaleAllocation rows, V54 refuses to guess from today's ProductComposition. This matters because an old/replacement sale may have used different physical colors.

In that case:

- raise `SaleDayDeleteError`,
- delete nothing,
- transaction rolls the entire action back,
- user sees that exact reversal could not be proven.

This is intentionally safer than deleting the report while silently failing to restore old stock.

## Inventory movement history

V54 follows the existing supported SaleLine reversal design: original InventoryMovement audit rows are not raw-deleted. Reversal creates the normal compensating stock movement through the existing sync engines.

Therefore current stock balances return, while audit history still records that a sale existed and was recalculated/reversed.

Do not replace this with raw InventoryMovement deletion unless the user explicitly requests a different audit policy.

## Capital / accounting effect

V54 does not edit capital directly.

Reversal naturally restores the balance sheet effects:

- finished inventory increases back by the stock/cost previously sold,
- Digikala receivable decreases by the removed net sale receivable,
- Dia receivable decreases by the removed Dia sale receivable,
- report gross/fee/COGS/profit disappear because their SaleLine/Dia rows no longer exist,
- capital therefore returns by reversing the sale profit contribution through the same components used by normal accounting.

No historical SaleSnapshot is recalculated before deletion; it is simply deleted with its SaleLine after the supported reversal is complete.

## V46 preservation

V54 does not alter:

- `core/final_services.py`,
- `core/sale_inventory_v19.py`,
- `core/variant_sale_v12.py`,
- `core/dia_gallery_v45.py`,
- any stock-location business rule.

All Darma-backed sale creation remains HOME-only under V46. Deletion restores the exact existing allocations; historical allocations that legitimately point to an older location are returned to the recorded location rather than rewritten.
